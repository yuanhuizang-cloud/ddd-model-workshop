## 八题参考答案


统一结构：先讲业务问题，再讲建模决策、为什么不选另一条路、失败时怎么办，最后给可验证证据。以下是示范场景，学习者应用自己的真实项目替换，不背成自己履历。

### Q1｜DDD 和 MVC／三层架构有什么区别？为什么采用？

**观察来源**：I1（上海爱数/盈峰环境），I3（WPS）。以下回答为原创。

**参考回答**：MVC 主要组织交互与展示职责，三层架构组织技术职责；DDD 关注团队如何理解业务、建立语言与模型，并让代码持续表达它们，二者可以组合。以退款为例，客服、用户与系统任务都能退款，若“不能超过可退金额”的规则分别落在三个 Service，很容易出现语义漂移。我会先与业务明确“实付、已退、冻结退款额”，再让退款相关聚合维护不变量，应用服务负责鉴权、事务和调用顺序。不会因为用了四个目录就说采用了 DDD，也不会把所有查询都包装成复杂领域对象。

**取舍**：简单报表或配置 CRUD 继续用轻量实现，复杂规则集中处投入建模。多一层抽象必须减少规则重复或缩小变更影响。

**验证证据**：同一规则从所有入口触发结果一致；无数据库领域测试能覆盖主要分支；真实需求变更涉及文件和跨团队沟通范围可追踪。没有测量就不报虚构百分比。

**追问**：业务简单时仍要统一语言吗？——可以保留语言和边界意识，而不强制全套战术模式。

### Q2｜限界上下文、子域、微服务分别是什么？怎么判断拆分合理？

**观察来源**：I3 的服务拆分；I1 的微服务划分。以下术语组合和案例为课程延展。

**参考回答**：子域是业务问题的分区；限界上下文是在一定范围内让语言和模型保持一致的边界；微服务是运行与部署选择。销售侧的订单强调价格和成交承诺，履约侧强调库存分配、包裹和时效，把两边共用一个巨型 Order 会让双方变化相互牵制。我会标出团队所有权、业务用词、变更节奏、集成契约和一致性要求，再决定是否形成两个上下文。两个上下文可以先在同一进程内通过接口协作，不能从一张实体关系图直接推出两个服务。

**取舍**：拆服务获得独立发布、扩缩容和故障隔离，但要支付网络失败、契约演进与运维成本。如果每次需求仍需联动发布，边界可能不稳定，或共享数据写入造成耦合。

**失败与验证**：消费者未知字段、重复事件、接口超时不能污染本地模型；做契约兼容测试、单方部署演练，检查共享写库和同步调用环路。服务数量没有目标值。

### Q3｜聚合怎么划？订单、订单项和库存放一起吗？

**观察来源**：课程自编高级追问，不能标为已核实原面经题。

**参考回答**：先列业务不变量，不从外键和“有一个 List”开始。订单提交时“行项目金额加运费减优惠等于应付金额”需要在同一版本下成立，可由订单聚合保护。库存属于不同竞争资源，若把一个商品的库存挂进每个订单，既失去唯一责任边界，也无法约束多订单争抢。通常由库存预留能力管理可售数量，订单根据预留结果推进到已确认；业务是否接受等待、缺货撤销或拆单，要先与领域专家确认。

**取舍**：大聚合容易加载无界历史、放大锁与版本冲突；过小聚合可能把真实强约束拆散。按 ID 引用其他聚合是常用手段，聚合边界不等于必须一次加载所有历史流水。

**失败与验证**：模拟两请求读同版本，保证一个失败或重新判定；检查库存不足、取消释放、重复回调。若某规则绝不能短暂违反，应调整边界或提供相应原子协议，而不是以“最终一致”四字跳过业务风险。

### Q4｜应用服务、领域服务、实体方法和仓储如何分工？生命周期谁管？

**观察来源**：I1 对象生命周期；其余为课程自编追问。

**参考回答**：创建时由构造函数或工厂形成有效对象；持续身份和状态变化由实体表达；天然属于对象的规则放在对象方法中；不自然属于单个实体但有明确业务含义的规则可用领域服务。应用服务加载对象、安排事务、调用规则并保存；仓储负责恢复和保存领域状态，不应把每张表都自动变成一个仓储。以撤销预订为例，预订判断是否已开始、是否允许取消，取消费用策略可以独立建模，应用服务把结果持久化并登记待发事件。

**取舍**：Go 不必模仿 Java 建大量继承结构；Python 的约定式封装也不能代替规则入口。查询可使用专用读模型，没必要为了分页重建全部聚合。

**失败与验证**：重建对象不得重新触发“首次创建”事件；无效持久化数据要显式失败或走迁移。内存仓储返回共享可变指针会绕过保存契约，测试替身需要复制或隔离状态。用仓储契约测试与真实数据库 round-trip 验证。

### Q5｜有了聚合根为什么还会超卖？乐观锁就够了吗？

**观察来源**：课程自编高级追问。

**参考回答**：对象方法只保证它看见的状态合理，两个进程都读取剩余一个名额时，可能各自判断成功。持久化必须协同维护约束，例如用版本号条件更新并检查影响行数，或在数据库用原子扣减条件。冲突后不能直接重复保存旧对象，必须重新读状态、重新执行规则；需要限制重试次数，避免热点请求互相放大。

**取舍**：乐观锁适合冲突可控场景；高冲突资源可以评估行锁、队列串行化、预留额度或业务分片。业务幂等与并发锁解决不同问题：前者识别同一意图的重试，后者协调不同意图争用状态。

**失败与验证**：并发发起 N 个独立请求，成功数不能超容量；同一 request_id 重试不能再次扣减；进程超时后重试要能读取首次结果。检查冲突率、等待时长和业务拒绝率，而不只看 HTTP 成功率。

### Q6｜领域事件什么时候发？数据库成功、MQ 失败怎么办？

**观察来源**：I4 明确记录“如何发送领域消息”。答案为课程原创。

**参考回答**：先区分进程内领域通知与对外集成消息。领域事件表达已经发生且有业务意义的事实；对外 payload 应是稳定契约，避免直接序列化整个聚合。写库前发送可能出现事务回滚但消息已生效；提交后直接发送则存在进程崩溃导致漏发的窗口。可把业务状态与 Outbox 记录写入同一本地事务，再由 relay 重试发送。它把“必须发”的意图持久化，不等于网络发送与数据库瞬时原子完成。

**取舍与失败**：relay 发出后、标记前崩溃会重复投递。消费者以 `(consumer, event_id)` 唯一键去重，并把去重记录与本地业务副作用置于同一事务；提交后确认消息。外部 RPC 副作用另需对方幂等键或状态核对。聚合内顺序可配版本号，跨聚合不默认全局有序。

**验证证据**：注入提交后宕机、发送后宕机、重复与乱序事件；核查业务效果只出现一次，积压可回收、死信可定位。观察最老未发事件年龄、重试次数、消费延迟。

**第一手来源**：https://microservices.io/patterns/data/transactional-outbox.html ，https://microservices.io/patterns/communication-style/idempotent-consumer.html 。本题为结合模式的原创设计回答，非网页逐句翻译。

### Q7｜钱包转账跨两个聚合怎么办？“一个事务只能一个聚合”是铁律吗？

**观察来源**：从用户提供博客衍生的课程代码评审题，不是真实面经原题。

**参考回答**：先界定系统边界。同库、同服务且业务要求同步原子完成时，可以明确采用一个本地事务协调两个账户的变化，并承认这是需要评审的跨聚合事务，而不是把所有账户合成巨型聚合。若经常跨相同边界强一致更新，应重新检查模型。交易顺序按稳定账户 ID 加锁可降低死锁，失败仍需完整回滚；还要验证正金额、同币种、账户状态、额度和转账幂等键。

**跨系统取舍**：两个外部钱包通常无法靠本地事务获得原子性。需要可追踪的转账流程与中间状态，例如发起、已扣款、待入账、完成、补偿中；具体是否接受预留、补偿取决于业务。网络超时只代表结果未知，不能直接当失败退款，否则对方已入账时会造钱。

**验证证据**：同一业务键的重复请求必须收敛到同一结果；余额与账务流水核对；模拟扣款后断网、入账响应丢失、补偿重试。钱包教学例子不构成生产账务系统的完整设计。

### Q8｜老系统如何落地 DDD？什么情况下会收缩使用？

**观察来源**：课程自编迁移题；不对应已核实的真实面经原题。

**参考回答**：先选一个规则复杂、变化频繁且能隔离的业务切片，例如退款资格判定。记录旧行为与业务术语，补特征测试；在边界处把旧数据翻译成新模型，建立单一写入责任，再逐步切流。不要一次重写全部系统，也不要让新旧模型长期同时写相同事实。双写需要可靠同步、可核对水位和回滚方案，不能只写两个调用。

**取舍**：迁移成本来自模型理解、兼容协议和团队习惯。如果业务始终简单、团队规模很小，或抽象只有转发代码而没有保护规则，可以删掉无价值的层和工厂，保留语言、不变量及责任边界。应说清放弃的是哪些实现负担，而非宣布 DDD 对任何系统都无效。

**验证证据**：灰度比较业务结果，跟踪差异并由领域专家解释；演练切回旧路由；记录变更周期、跨模块改动范围、规则回归缺陷和性能。报告测量方法与样本，不能为了面试捏造收益。
